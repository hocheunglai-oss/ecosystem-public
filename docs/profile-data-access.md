# Profile data access and recovery

Supplier master writes (`create`, `update`, `archive`) require a real active administrator or SPC trader. The API and private SQL operations both check that authority. A role preview never permits writes. Regular active members can read active supplier profiles and add their own private tabs.

Supplier Profiles now opens a centered name list with each legal name and SPC name on one line. SPC VIEW switches to the Singapore comparison table, where members can filter by supplier PIC and grade. A real SPC trader or administrator can change a Singapore supplier PIC in that table. Each successful supplier update, including a PIC change, earns one shared contribution through the supplier revision; idempotent retries do not count twice. Shared profile tab content edits also earn one contribution, while private tabs and title-only changes do not.

Creating a supplier is currently limited to Singapore. The server generates its canonical UUID, source key and authenticated user provenance. Typed legal-name changes are marked `needs-review`; they do not claim official-registry verification. Imported source records and historical revisions remain available. `background` is separate from immutable import evidence and is included in revision snapshots.

Archive removes a supplier from live lists, detail lookup and report access without deleting its identity, operational data, reports or history. The service-only `eco_restore_supplier` operation requires an active operator administrator and `{requestId, operatorId, id, revision}`. Recovery checks current revision and conflicting active legal/short names, records a new snapshot and audit event, and supports exact request retries. Never update archive columns directly as a routine recovery path.

## Profile tabs

`shared/profileTabs.ts` is the client/server contract. `/api/profile-tabs/list` takes `kind` and `id`. `save`, `delete` and `reorder` accept a request UUID, target, visibility and expected scope revision. `save` replaces one complete scope atomically, so tab management can add, rename, remove and reorder together. Shared and owner-private revisions are independent; an absent scope starts at revision zero. A saved empty scope is intentional and must not be replaced by default UI tabs.

The supported kinds are supplier, buyer, country and port. Country IDs retain their existing exact names, including spaces and Unicode. Supplier targets require a canonical active supplier UUID. Buyer/country/port master records are still application references: their ID syntax is checked, but server-side existence cannot be established until those master records are persisted. This limitation does not weaken the owner boundary.

Private ownership is derived exclusively from the current live session, never a supplied owner ID. Another application administrator cannot list or retrieve a user's private collection. All private collections are hidden during role preview, including administrator preview. Custom tab IDs retain their original target/owner/visibility after removal and cannot be republished into another scope. To share information intentionally, create a new shared tab and enter the content explicitly.

Private text, titles and snapshots stay in private RLS-enabled tables with no browser-role table grants. Audit events include operation, target, scope revision and count only. They do not include private titles or content. Supplier shared tabs require administrator/SPC authority; shared location/buyer tab operations retain the existing active-member rule. Current location/buyer interfaces continue to use their existing rich shared-tab model while adopting the server private-tab collection.

Exact retries return the committed result before checking a newer scope revision. A changed payload with the same request UUID is rejected. A new request using an old revision is rejected; clients must explicitly reload and reconcile rather than overwrite. Revisions are retained for recovery; removing a tab removes it from the current collection but does not erase historical snapshots. Application-level privacy is not end-to-end encryption: authorized database operators still have infrastructure access.

## Country and port hierarchy

Active navigation, search, creation and port relationships use countries and ports only. `flattenLocationHierarchy` removes old grouping relationships without inventing ports or renaming actual locations. Migration version 1 retains group metadata in `legacyLocationAreas` and original port relationships in `legacyPortAreaIds`; original area knowledge keys, revision history, contribution/Hats targets and commercial records remain unchanged as archived evidence. The compatibility knowledge resolver can read those records, but rejects new writes to archived area targets. Archived notes are not copied into country tabs or counted again as contributions.

Existing attachment folder, item and Blob IDs remain unchanged. Referenced old group folders appear as ordinary named folders below their country; active upload destinations resolve to the country. The migration does not delete stored files. Preserve these archives during later server migration and reconcile their old IDs explicitly rather than running a reset or replacing a user's local store.

Country/port/buyer private tabs use the authenticated API only. Their titles and text are excluded from local knowledge, shared search/history and reward counts. Owner/preview/target changes immediately hide retained editor and manager snapshots. Conflicts retain the draft until explicit reload, and an unknown response retries the same request UUID and payload.

## Verification

`tests/suppliers-sql.test.mjs` applies all migrations to an isolated PostgreSQL instance and checks live roles, owner isolation, immutable identity, revision races, idempotency, preview restrictions, audit rollback, archive recovery and report metadata access. API/input tests live in `tests/suppliers.test.ts` and `tests/profile-tabs.test.ts`.

`tests/locations.test.ts` verifies lossless legacy relationship migration, read-only archives and stable attachment references. `tests/location-flattening.e2e.mjs` and `tests/private-profile-tabs.e2e.mjs` run in the browser CI job at 1440, 320 and 390 pixels, light/dark, Chromium/WebKit. Private-tab checks cover country/port/buyer CRUD, reorder, stale-revision drafts, unknown-response retries, preview and administrator-owner changes, no shared/local record contamination, and selected-tab visibility. Location checks preserve original attachment bytes in Chromium. On the isolated macOS WebKit runtime, creating an IndexedDB Blob fixture fails with `UnknownError: Error preparing Blob/File data to be stored in object store`; those cases use retained link metadata instead and do not establish Blob-byte recovery coverage. Native Safari and physical phones are not tested by these emulated browser checks.

`scripts/verify-suppliers-cloud.mjs` is an explicit operator fixture test. It stays inert until invoked with `--allow-cloud-mutations`, verifies the canonical ECO target/deployment/source/migrations, and uses disposable identities and suppliers only. It additionally checks real cross-client private tabs, ordinary trader write denial, SPC creation/archive, private report storage and signed downloads. Its private recovery journal records fixture identities and object hashes before publication; cleanup checks ownership before removing fixtures. Never run it against an unreviewed release or before its migrations and private report bucket are configured.

## PDF publication journal

`scripts/suppliers/publish-reports.mjs --manifest <private-manifest> --apply` persists the exact report IDs, hashes, target and operator in an owner-only `.request.private.json` file before publication. Each confirmed report is added to an atomically replaced, fsynced `.receipt.private.json`; existing successes are retained throughout retries. Matching server metadata and actual object bytes recover a lost response without repeating a successful registration. Missing metadata or bytes for a known successful publication stop the operation for recovery review. A generic provider error is never interpreted as a missing object.

Only one publisher can hold the request lock. A crash may leave `.request.private.json.lock`; check the process and provider state using the private journal before an operator removes that lock. Never discard request/receipt files to force a retry, and never change a manifest after its request has been saved. A changed report version needs a new reviewed manifest and immutable report UUID. Publication does not attempt an automatic compensating delete after ambiguous failures: it preserves the owned PDF and journal so the same request can be reconciled safely.
