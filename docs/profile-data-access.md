# Profile data access and recovery

Singapore supplier master writes (`create`, `update`, `archive`) require a real active administrator or SPC trader. Active members may manage non-Singapore supplier records. The API and private SQL operations recheck stored country and authority. A role preview never permits writes, and TEST cannot publish shared changes. Regular active members can read active supplier profiles and add their own private tabs.

Supplier Profiles opens a centered name list with each legal name and SPC name on one line where space permits, wrapping safely on phones. SPC VIEW switches to the Singapore comparison table, where members can filter by supplier PIC and grade. A real SPC trader or administrator can change a Singapore supplier PIC in that table. Each successful supplier update, including a PIC change, earns one shared contribution through the supplier revision; idempotent retries do not count twice. Shared profile tab content edits also earn one contribution, while private tabs and title-only changes do not.

Supplier creation validates the canonical country/port pair and the actor's permission for that country. Unmapped ports must not silently become Singapore. The server generates the canonical UUID, source key and authenticated user provenance. Typed legal-name changes are marked `needs-review`; they do not claim official-registry verification. Imported source records and historical revisions remain available. `background` is separate from immutable import evidence and is included in revision snapshots.

Archive removes a supplier from live lists, detail lookup and report access without deleting its identity, operational data, reports or history. The service-only `eco_restore_supplier` operation requires an active operator administrator and `{requestId, operatorId, id, revision}`. Recovery checks current revision and conflicting active legal/short names, records a new snapshot and audit event, and supports exact request retries. Never update archive columns directly as a routine recovery path.

## Profile tabs

`shared/profileTabs.ts` is the client/server contract. `/api/profile-tabs/list` takes `kind` and `id`. `save`, `delete` and `reorder` accept a request UUID, target, visibility and expected scope revision. `save` replaces one complete scope atomically, so tab management can add, rename, remove and reorder together. Shared and owner-private revisions are independent; an absent scope starts at revision zero. A saved empty scope is intentional and must not be replaced by default UI tabs.

The supported kinds are supplier, buyer, country and port. Country IDs retain their existing exact names, including spaces and Unicode. Supplier targets require a canonical active supplier UUID. The profile-tabs API retains its historical syntax-only validation for buyer/country/port references; the separate shared location API now persists canonical country/port records, and general attachment operations validate those shared targets. This does not broaden private ownership.

Private ownership is derived exclusively from the current live session, never a supplied owner ID. Another application administrator cannot list or retrieve a user's private collection. All private collections are hidden during role preview, including administrator preview. Custom tab IDs retain their original target/owner/visibility after removal and cannot be republished into another scope. To share information intentionally, create a new shared tab and enter the content explicitly.

Private text, titles and snapshots stay in private RLS-enabled tables with no browser-role table grants. Audit events include operation, target, scope revision and count only. They do not include private titles or content. Supplier shared tabs follow country-specific supplier permissions. Shared location/buyer tab operations retain the existing active-member API rule; buyer/credit interfaces remain gated to administrators until ECO 2.0. Current location/buyer interfaces continue to use their existing rich shared-tab model while adopting the server private-tab collection.

Exact retries return the committed result before checking a newer scope revision. A changed payload with the same request UUID is rejected. A new request using an old revision is rejected; clients must explicitly reload and reconcile rather than overwrite. Revisions are retained for recovery; removing a tab removes it from the current collection but does not erase historical snapshots. Application-level privacy is not end-to-end encryption: authorized database operators still have infrastructure access.

## Country and port hierarchy

Active navigation, search, creation and port relationships use countries and ports only. `flattenLocationHierarchy` removes old grouping relationships without inventing ports or renaming actual locations. Migration version 1 retains group metadata in `legacyLocationAreas` and original port relationships in `legacyPortAreaIds`; original area knowledge keys, revision history, contribution/Hats targets and commercial records remain unchanged as archived evidence. The compatibility knowledge resolver can read those records, but rejects new writes to archived area targets. Archived notes are not copied into country tabs or counted again as contributions.

Existing attachment folder, item and Blob IDs remain unchanged. Referenced old group folders appear as ordinary named folders below their country; active upload destinations resolve to the country. The migration does not delete stored files. Preserve these archives during later server migration and reconcile their old IDs explicitly rather than running a reset or replacing a user's local store.

Country/port/buyer private tabs use the authenticated API only. Their titles and text are excluded from local knowledge, shared search/history and reward counts. Owner/preview/target changes immediately hide retained editor and manager snapshots. Conflicts retain the draft until explicit reload, and an unknown response retries the same request UUID and payload.

A country with exactly one registered port opens the same combined profile from either index. Both original country/port shared sources and owner-private collections remain distinct. Same-titled tabs must retain their source identity, and saves go to that original target. Adding a second port restores independent views without moving data. Private collections stay first in the shared manager and tab strip; a combined view never broadens ownership.

## Verification

`tests/suppliers-sql.test.mjs` initializes an isolated PostgreSQL instance using the public baseline and append-only migrations, then checks live roles, owner isolation, immutable identity, revision races, idempotency, preview restrictions, audit rollback, archive recovery and report metadata access. API/input tests live in `tests/suppliers.test.ts` and `tests/profile-tabs.test.ts`. Never replay the public baseline on an existing production database.

`tests/locations.test.ts` verifies lossless legacy relationship migration, read-only archives and stable attachment references. `tests/location-flattening.e2e.mjs`, `tests/country-port-profiles.e2e.mjs` and `tests/private-profile-tabs.e2e.mjs` run in browser CI at 1440, 320 and 390 pixels, light/dark, Chromium/WebKit. The unified profile harness covers supplier/country/port/buyer private tabs, rich text/tables, ordering, revisions, retries, preview and owner changes, no shared/local record contamination, and selected-tab visibility. Combined-profile checks preserve original source targets. Location checks preserve original attachment bytes in Chromium. On the isolated macOS WebKit runtime, creating an IndexedDB Blob fixture fails with `UnknownError: Error preparing Blob/File data to be stored in object store`; those cases use retained link metadata instead and do not establish Blob-byte recovery coverage. Native Safari and physical phones are not tested by these emulated browser checks.

Cloud fixture verification is a separate, explicitly authorized operator procedure against the exact pinned release. It uses owned disposable data, proves cleanup and retains private recovery evidence. Local browser and database tests alone do not establish a production pass.

## Protected reports and recovery

General profile files have a separate protected bucket and authenticated catalog. Prepare/complete operations reserve capacity, verify the original byte count, digest and immutable object version, then publish metadata only after authorization is checked again. Downloads require active membership; Singapore supplier writes additionally require an administrator or SPC trader. VIEW AS and TEST cannot write. Links and folder changes use the same server permission and revision checks. Archive retains identity and recovery evidence; it does not erase original browser copies or immutable object bytes.

An explicit import considers only the current real owner's local attachments and active country/port/supplier targets. Missing-owner, unsupported and missing-byte records stay local. Importing one user's files never publishes another user's browser records. Old item/folder IDs and bytes remain recoverable, and failed uploads keep a separate owner-scoped local original. Nightly capture includes both complete files and pending object bytes; pending uploads are not represented as published files. Captures fail on an unexpected bucket, path, version or byte mismatch instead of silently omitting it.

Available source PDFs use protected storage and authenticated short-lived downloads. Immutable report IDs, hashes and source references distinguish report versions. Publication preserves exact-request receipts through retries and reconciles ambiguous responses against metadata and object bytes. A generic provider failure must never be treated as a missing object or trigger an automatic destructive rollback. Keep publication manifests, operator identities, locks, receipts and recovery runbooks private. Do not claim a PDF is stored merely because its text or summary was reviewed.
